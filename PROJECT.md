# iwatched — Project Brief

Personal tracker for **movies, series and books**. Mark what you've seen/read and keep optional progress.

> **Naming:** the app is called **iwatched**. The repository (`hermes-media-tracker`) and the Dart package (`media_tracker`) keep their historical names — renaming them would break the GitHub Pages URL/`base href` and every `package:media_tracker/…` import.

## Product Vision (from Daniel, 2026-08-21)

Track three media types with different granularity:

| Type | Core | Extended |
|------|------|----------|
| **Movie** | "watched" status | progress with timestamp and/or percent |
| **Series** | per-**episode** "watched" (default: check off a whole episode) | progress percent / timestamp |
| **Book** | "read" status | percent or page-based progress |

### Metadata
- **Movies & Series:** TMDB (posters, descriptions, seasons, episodes). API key required.
- **Books:** OpenLibrary API **or** Google Books API (decision open — OpenLibrary needs no key).

### Persistence
- **Supabase** (Postgres) stores all status/progress data.
- **JSON export/import** for backup and portability.

### Bonus (last, optional)
- ISBN **text entry** is live (Phase 6a). ISBN **barcode scanning** via `mobile_scanner` (camera) is deferred (Phase 6b) to a future native/Android build — the plugin needs a platform camera and cannot run in the Flutter-web test loop.

## Platform
- **Flutter Web app**, deployed to **GitHub Pages** (debug/test loop).
- UI language: **German / English toggle** in settings (German is the default). The toggle also switches TMDB metadata and search language; OpenLibrary is not localized (see known limitations).

- [x] **Phase 5c — Reading log:** exact "pages read per period" instead of the old approximation. Migration `0003_reading_log.sql` adds `public.reading_log` (`id`, `user_id` → `auth.users`, `media_item_id` → `media_items` `on delete cascade`, signed `pages`, `logged_at`, `created_at`) with owner-only RLS. Every commit of a **book's** page position writes one entry: the signed delta to the previous `progress_current` — the single funnel is `LibraryProvider._applyTracking` + `readingLogDelta` (`lib/providers/tracking_rules.dart`), fed by the page input, the sliders' `onChangeEnd` (a drag release, never each intermediate step), `completed` (logs the remaining pages) and the `planned` reset (logs the whole reduction as a negative entry). Movies/series and books without `total_pages` never log (no page position). A failing log insert is swallowed — it can never break the progress update (and the app keeps working before the migration is applied). `computePagesRead` (`lib/services/stats_calculator.dart`) sums the signed `pages` over the half-open `[start, end)` window, so corrections subtract and a period can legitimately be negative; the stats screen loads the log next to items + episodes. **History is preserved:** the migration's backfill gives every already-completed book a single entry with its full page count dated at `completed_at` (only when it has no entry yet), so past periods do not regress against the old approximation.
- [x] **Phase 5b — Library search, filters & sorting:** the library can be searched, filtered and sorted **client-side on the already-loaded list** (no server round-trip, no DB query, no pagination). A toggled search field filters live over the **title** of every kind and additionally over a **book's authors**; the match is case-insensitive and diacritic-tolerant (`normalizeSearchText` folds umlauts/accents/ß, so "herr" finds "Der Herr der Ringe" and "muller" finds "Müller"). Two horizontally scrollable chip rows filter by **media type** (all/movies/series/books) and **status** (all/planned/in progress/completed/dropped); search and both filters combine with a logical **AND**. Sorting offers **recently added** (`created_at` desc, default), **title A–Z** (case-insensitive, leading articles kept), **release year** (desc) and **progress** (desc) — all stable for equal keys, with missing fields sorted last. A localized result counter ("12 Treffer von 48" / "12 results of 48", singular-aware) appears while a search/filter is active, next to a quick "reset filters" action, and the library gets its own **"no matches"** empty state (clearly distinct from the "library is empty" one). All logic is pure and unit-tested in `lib/services/library_filter.dart`; the screen's search/filter/sort state is **session-only** (never persisted) and the provider's list is never modified.
- [x] **Phase 6a — ISBN text search:** the search field also accepts an **ISBN** (typed, no camera). A pure `parseIsbn` (`lib/services/isbn.dart`) normalizes the input (strips separators plus an `ISBN` / `ISBN-10:` / `ISBN-13:` prefix, upper-cases a trailing `X`) and validates the **check digit** of ISBN-10 and ISBN-13 — a deliberate guard so ordinary 10-/13-digit numbers are *not* mistaken for an ISBN and keep going through the normal text search. On the `Books` and `All` scopes a valid ISBN runs an OpenLibrary **ISBN lookup** instead of the title query (the `Movies` / `Series` scopes keep their normal TMDB search), signalled by a small "ISBN-Suche / ISBN lookup" label; the hit renders like any other book (cover, title, authors, year) with the usual detail sheet + "Add to library" (duplicate handling included), and a miss shows a localized "no book for this ISBN" state that names the ISBN. Because `/isbn/<isbn>.json` resolves to an **edition** (`/books/OL…M`), `OpenLibraryClient.lookupByIsbn` reads the edition's linked **work** (`works[0].key`) and stores the work key as `external_id` — so an ISBN add still dedups against a later title search; author names (absent on the edition payload) come from one best-effort `q=isbn:…` search call. All new strings are localized (DE/EN).

- [x] **Phase 8 — Library status badges in search results:** each search hit (movie / series / book) shows up to **two compact badges** right next to the media-kind chip and the year. **`badgeInLibrary`** ("In der Bibliothek" / "In library") appears when the title is already tracked — **any** status; **`badgeWatched`** ("Gesehen" / "Watched") appears when that entry is `completed`. A completed title therefore shows **both** badges, an untracked hit shows **none** (no empty placeholder). The external-id → library mapping is a **single source of truth**: `mediaIdentity(externalSource, externalId)` (`lib/models/media_item.dart`) is exposed as `identityKey` on the search hits (`TmdbSearchResult`, `BookResult`) *and* on `MediaItem`, and is used both when a hit is **stored** (`toMediaItem` now takes the source from the `kExternalSource*` constants) and when the library is **looked up** — so an ISBN hit, which is resolved to its **work** key (Phase 6a), matches a normal title search and vice versa. `LibraryProvider` keeps a prebuilt `Map<identityKey, MediaItem>` index, rebuilt once on every list change (`_setItems`), so `lookup` / `badgeState` are O(1) — never a per-hit scan over the whole list. The search screen calls `LibraryProvider.ensureLoaded()` once on open (deferred to the first frame) so the badges work even when the library tab was never opened; the load is attempted at most once and a failure is swallowed, so the badges simply stay hidden and the search keeps working (no crash, no error in the search). The badges are `LibraryBadge` (`lib/widgets/media_widgets.dart`), deliberately distinct from the neutral media-kind `PillBadge` and the year text: *in library* uses `primaryContainer` + `bookmark`, *watched* the tertiary/completion `tertiaryContainer` + `check_circle`. The **detail sheet** mirrors the state: a completed tracked entry now reads "Bereits gesehen" / "Already watched" (`alreadyWatched`) instead of the generic "already in your library" — no other change to the sheet. - [x] **Phase 10 — Season pre-selection when opening a series:** opening a series in the library no longer always lands on **season 1**. A pure `initialSeasonFor(episodes, availableSeasons)` (`lib/providers/series_rules.dart`) returns the season the user is currently in: **nothing watched** → the first season (unchanged); **something watched** → the season of the **most recently watched** episode (`watched_at`, a missing timestamp counts as the oldest, ties broken by season/episode so the choice is deterministic); if that **base season is fully watched** and a **later** season exists, the **next** available season is pre-selected (where you'd continue — also covers the "season 1 done, season 2 not started" case); a **fully watched last season** stays selected, and a series with a **single season** always lands on it. Unit tests cover all branches (mid-season, completed→next, last season, single season, gaps in the numbering, irregular `watched_at`, empty list → `null`) and widget tests cover "opens on the season of the last watched episode" plus "a manual switch is not reset by a rebuild".

- [x] **Phase 11 — Instant library adoption of new items + open-from-search:** adding a title from a search-result sheet is now reflected **immediately** and **without any extra query**. A new `LibraryProvider.adoptInserted(item)` places the freshly stored row (the one the DB returns from the insert) into the in-memory list — **prepended** when new, **updated in place** when it is already tracked (matched by `id` first, then by external identity `identityKey`) so a re-adopt can never duplicate — and rebuilds the existing O(1) identity index through the **same** `_setItems` path the list loads use (no duplicated index logic). The result: the library list, the category-tile counts and the search-result badges all update the instant the insert lands. Previously only `repository.insert(...)` was called and the in-memory list was left untouched, so a new title only appeared when something else happened to trigger a reload — the reported 20–30 s gap. Both search add paths funnel through it: **"Zur Watchlist / Add to watchlist"** adopts the inserted `planned` row, and **"Schon gesehen / Mark as watched"** (`insertAsWatched`) adopts the row and then runs the **existing** automation paths (`LibraryProvider.setStatus` for a movie/book; `ensureEpisodes` + `markAllEpisodesWatched` for a series — `series_rules` is never bypassed), so the returned and adopted copy is the **derived final state** (series: status/progress from the checked-off episodes). The two `library.load()` calls that used to paper over the stale list were removed. **Never-loaded guard:** when no load has ever been attempted (`_loadAttempted == false`) `adoptInserted` deliberately leaves the list alone (a one-entry list with wrong tile counts would be worse) and kicks off a one-time `ensureLoaded()` — in practice the search screen already triggers that load on open, so this is only a safety net. The sheet itself now carries the localized **"Öffnen" / "Open"** offer instead of a snack-bar action: after a successful add the (deliberately still open) sheet shows its "Bereits in deiner Bibliothek" / "Bereits gesehen" state **plus** a clearly visible `OutlinedButton.icon` ("Öffnen" / "Open"). Tapping it closes the sheet in a **controlled** way (`mounted && ModalRoute.of(context)?.isCurrent == true`, with the app-level `Navigator` captured before the pop) and then opens the new entry's `MediaDetailScreen` (a series lands on its current season, Phase 10). A snack bar would render **behind** the open sheet's modal barrier — invisible and un-tappable — so it no longer offers the action (the redundant success snack bar was dropped entirely; the sheet's own state is the confirmation). A series whose episodes could not be loaded shows that note inline in the sheet. All new strings are localized (DE/EN). Tests cover: the index knows the item's badge immediately after adopting, an update replaces instead of duplicating (by id and by identity), a never-loaded library is not adopted into, the search badge appears **without a reload** after both add actions, the series adopts its derived `completed`/100 % state, and the **open offer in the sheet** opens the **right** title for both add actions in the TMDB **and** book sheet (with no `SnackBarAction` present). No network in any test.

- [x] **Phase 13 — Sign in with an email code as well as the magic link (iOS PWA fix):** sign-in no longer depends on the magic link landing in the right context. Supabase's sign-in email already carries **both** a clickable link **and** a one-time code, so the login screen's "check your inbox" step now also offers a **numeric code field** (6–8 digits, `TextInputType.number`, autofocused) with an **"Anmelden / Sign in"** action, an **inline** error box (wrong code, expired code, rate limit, offline — all localized, shown while typing, not as a passing snack bar), a short **resend cooldown** against accidental spam and a **"andere E-Mail-Adresse verwenden / use a different email"** way back to the email form. The link keeps working exactly as before — nothing was removed. **Why:** on iOS the magic link opens in the mail app's **in-app browser** (or Safari) while the app runs as a **homescreen PWA**, and iOS keeps **separate storage between those contexts** — the session the link creates therefore never reaches the PWA, so the user had to request a fresh link every time (systemic, not a code bug). Typing the code creates the session in the very browser/PWA context the app is used in, with no cross-context hand-off. Implemented as `AuthProvider.verifyEmailCode` (Supabase `verifyOTP(email:, token:, type: OtpType.email)` — `email` is GoTrue's current name for the email magic-link/OTP verification type, `magiclink` is the deprecated server-side alias). `onAuthStateChange` still drives the state change (untouched). The `describeAuthError` helper was extended (rate-limit / expired / wrong-code / network) and is shared by the send **and** verify paths; messages are localized via the app language injected into the provider. **No Supabase schema/RLS change was needed.**

- [x] **Phase 14 — Sign in by pasting the magic link (the real iOS-PWA fix):** the login screen's second step no longer depends on the link opening in the right browser context. Its input field became a **multi-purpose field**: it accepts the numeric 6–8-digit code **and** a **pasted magic link** (or a bare token). A pure, unit-tested `parseAuthInput` (`lib/services/auth_input.dart`) classifies the input — **6–8 digits → `code`**; an `http(s)` URL carrying a `token` (or `token_hash`) query parameter → **`tokenHash`** (the parameter's value); a long opaque token on its own → `tokenHash`; anything else (empty, a foreign URL, digits glued to text) → **`invalid`**. Whitespace / line breaks around the input are tolerated and a wrapped URL is compacted before parsing, so a link a mail client split across lines still works. A `tokenHash` is redeemed through the new `AuthProvider.verifyEmailLinkToken` → Supabase `verifyOTP(tokenHash:, type: OtpType.magiclink)` (the installed **GoTrue 2.27.2 supports `tokenHash`**; the mail link carries `type=magiclink`), which returns a session **in the very browser/PWA context the app runs in** — no address bar, no context switch. The confirmation view now shows two localized (DE + EN) hints: a neutral info box ("tap the link — or paste it in the field below") and a more prominent **iPhone box** that explains you must **copy** the link (long-press → "Copy") instead of tapping it, because iOS opens a tapped link in Safari or the mail app's in-app browser, whose storage a homescreen-PWA cannot see. The field's keyboard changed from numeric to the normal text keyboard (it now takes URLs) and the placeholder says "code or link". Errors reuse the existing `describeAuthError`, extended with a `forLink` flag so a **used-up / expired** or invalid link gets link-specific wording instead of code wording (the mapping is not duplicated). Everything else is unchanged: resend + cooldown, "use a different email", the magic-link redirect and `onAuthStateChange`. **Why:** Supabase's sign-in mail only contains the 6-digit code if the project's mail template includes `{{ .Token }}`, and **editing the mail template is not possible on the free tier** (confirmed by the user) — so the Phase 13 code path, though implemented, is not usable on this project. Pasting the link needs **no template change** and **no schema/RLS change**.

- [x] **Phase 15 — Two fixes from real search / filter use:**
  - **The list title follows the filter.** The pushed library list (`LibraryListView`, `lib/widgets/library_view.dart`) derived its AppBar title from the `initialKind` it was opened with, so tapping the "Filme" banner and then switching the media-type chip to "Serien" kept the heading "Filme". The title is now derived from the **live filter state** (`_kindFilter`) via the existing `AppStrings.libraryListTitle` — Movies → "Filme", Series → "Serien", Books → "Bücher", All → "Bibliothek" (EN: "Movies" / "Series" / "Books" / "Library"), reactive, no navigation needed. No new strings.
  - **Search hits are ranked by popularity, not by the API's relevance order.** Searching e.g. "Star Wars" surfaced niche "Behind the Scenes" material above the actual films. The new pure `lib/services/search_ranking.dart` provides `rankSearchResults(query, results, titleOf:, popularityOf:)`: **tier 1** = hits whose normalized title (lowercase, diacritics folded, trimmed — the same `normalizeSearchText` the library uses) is *exactly* the query or *starts with* it (exact before prefix), **tier 2** = everything else; within a tier **descending popularity**, stable on ties (index tie-breaker), missing popularity = `0` (sorts last), empty query keeps the incoming order. `TmdbClient.search` applies it with `vote_count` (new tolerant `TmdbSearchResult.voteCount`, `0` when absent) — for `search/movie`, `search/tv` and `search/multi`; `vote_average` is deliberately *not* used. `OpenLibraryClient` extends its existing German-first partition instead of replacing it: `ratings_count` (new `BookResult.ratingsCount`, requested through the existing `fields` parameter) is the popularity signal with `edition_count` as fallback (`BookResult.popularity`), and each **language group** is then ordered by popularity (`rankByPopularity`) — German hits still come first, only *within* a group does popularity decide. The "All" scope keeps its round-robin interleaving of TMDB + OpenLibrary (each source is already ranked internally), the search limit stays 20, and ISBN lookup / badges / detail sheets / search UI are untouched.

- [x] **Phase 16 — Performance experiment: the full-bleed blur is gone from the category banners.** The Phase 12 banners laid a **blurred (`sigmaX/Y = 10`), dimmed copy of the newest cover** over the *whole* card (`Positioned.fill` → `ImageFiltered` + `ColorFiltered`). A Gaussian blur across a full-width card has to be **re-rastered on every repaint**, and the library landing screen shows **four** of them — the user reported noticeably lower FPS while scrolling since the banner rebuild. That layer is now **removed entirely**; the **theme gradient** (`cs.primary → cs.primaryContainer`) is the whole background again, exactly as in the cover-less fallback. **`_FanDeck` and the `_Scrim` are untouched** in geometry, order and text, and the fan's behind-card dimming is now a plain black overlay *inside* the rounded clip (same pixels as the previous darken filter — `darken(black, α)` composited equals a black layer at `α` — but without a per-card save layer). The now-unused `import 'dart:ui'` went with it, and a widget test asserts the banners build **no** `ImageFiltered` / `ColorFiltered` at all so the blur cannot creep back in. This is **deliberately only an experiment**: if the FPS do not improve on the user's phone, nothing further is optimized — then the browser is the ceiling. Behaviour is unchanged (label, count, banner tap → filtered list, gradient fallback without a cover, fan), no `cacheWidth` / `RepaintBoundary` / layout change, no new strings. *Supersedes the "blurred, dimmed hero also fills the whole card as the atmospheric background" detail of Phase 12.*

## Known limitations / backlog

- **Book titles are not localized.** OpenLibrary exposes titles at *work* level, which is usually the original title ("The Lord of the Rings", not "Der Herr der Ringe"); German titles only exist on the individual *editions*. A localized book title would need an extra editions lookup per book. *Deliberately deferred to the very end — current behaviour is acceptable.*
- **Specials (season 0) are not tracked.** The episode loader fetches only the numbered seasons (`season_number >= 1`); the specials season is skipped so it does not skew the derived progress (it is often a large, incomplete extras bucket). This is a pragmatic call for Phase 3b — specials can be added later behind their own toggle.
- **ISBN lookup stores the *work* key while showing *edition* metadata.** `/isbn/<isbn>.json` returns an edition (`/books/OL…M`), but the app tracks books per work, so an ISBN hit is resolved to the edition's linked work (`works[0].key`) and stored with that work key as `external_id` (title/cover/pages/year come from the edition payload, author names from a best-effort `q=isbn:…` search call). Upside: an ISBN add dedups against a normal title search. Trade-off: two different editions (different ISBNs) of the same work count as one entry, and edition-specific metadata (publisher, that exact printing) is not modelled.

## Decisions

1. **Supabase + auth model** → project `vqpkejsxfvaovhdomllw`; **magic-link (email) auth** with owner-only RLS. Chosen over an unauthenticated setup so a leaked publishable key cannot be used to read or write anyone's data.
2. **Metadata sources** → **TMDB** for movies/series (read access token, injected at build time via `TMDB_TOKEN`), **OpenLibrary** for books (no key, no auth). German search results are ranked first on a German UI instead of filtering, and books are excluded from the language-driven metadata refresh (works are not localized). Google Books was considered and dropped.
3. **Deployment** → GitHub Pages via GitHub Actions on every push to `main`; the web app is the debug/test surface, Android is the eventual target.
4. **Rules as pure functions** → page-progress deltas, series derivation, library filtering and stats aggregation live outside the widgets and are unit-tested. Business logic never sits inside a `build()`.
5. **Reading history** → a dedicated `reading_log` table rather than deriving pages from completion dates, so "pages read per period" is exact (see Phase 5c).
6. **Email-code sign-in next to the magic link** → Supabase sends the **link and the code in one email**; the login screen accepts either. Chosen because **iOS isolates storage between Safari and a homescreen-PWA**, so a link opened in another context never establishes the session in the PWA the user actually works in — the code is entered **in that context** and always lands. The magic-link path is kept unchanged (no feature lost), and no schema/RLS change is involved. See Phase 13.
7. **Paste-the-link sign-in (Phase 14)** → the login screen's second-step field accepts the **numeric code _or_ a pasted magic link**. Chosen because (a) Supabase only puts the 6-digit code in the mail when the project's mail template contains `{{ .Token }}`, and **editing the mail template is not possible on the free tier** (user-confirmed) — so the code path alone is not usable here; and (b) letting the user **paste** the link into the field redeems the token **in the PWA's own storage**, with no address bar needed and no template/schema/RLS change. The "what is this input?" decision therefore lives in a pure, unit-tested `parseAuthInput` (`lib/services/auth_input.dart`), not in the widget.
